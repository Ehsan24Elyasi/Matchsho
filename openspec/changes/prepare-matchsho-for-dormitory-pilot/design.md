## Context

مبنای این طراحی proposal همین تغییر و ممیزی ۳۰موردی ۲۰۲۶-۱۰-۰۲ است. برنامه FastAPI/SQLAlchemy با Alembic، فرانت HTML/JavaScript/Tailwind و Nginx دارد. PostgreSQL محیط عملیاتی هدف است، اما تست‌های قبلی عمدتاً SQLite و ترتیبی بودند. احراز هویت پایه، نقش ادمین، CSRF و migration حفظ می‌شوند؛ رفتار معیوب موجود قرارداد سازگاری محسوب نمی‌شود.

دامنهٔ مورد تأیید کاربر یک دانشگاه/خوابگاه با تعداد محدود دانشجوست. سه ذی‌نفع اصلی دانشجو، اپراتور خوابگاه و مسئول استقرار هستند. تغییرات فعلی working tree متعلق به کاربرند؛ پیاده‌سازی باید روی وضعیت موجود پیش برود و آن‌ها را بدون بررسی بازنویسی یا revert نکند.

## Goals / Non-Goals

**Goals:**

- حفظ حریم خصوصی و اعتبار نشست، حتی هنگام درخواست‌های هم‌زمان یا restart سرویس.
- پیشنهاد قابل‌پیوستن بر اساس رفتار واقعی و ترجیحات دوطرفه؛ رضایت قابل‌ردیابی اعضای گروه.
- ظرفیت و تخصیص قابل‌اتکا، خروج فرد بدون ازدست‌رفتن جای دیگران، تاریخچهٔ قابل‌بررسی توسط اپراتور.
- مسیر کامل فارسی/RTL روی موبایل، دسکتاپ و keyboard؛ نمایش درست خطا و امکان ادامه پس از refresh.
- کد تفکیک‌شده، migration امن، ارسال ایمیل پایدار و شواهد آزمون/بازیابی برای پایلوت.
- پوشش هر ۳۰ یافتهٔ ممیزی؛ نگاشت آن‌ها در tasks مستقل از فایل ممیزی بیرون repository ثبت می‌شود.

**Non-Goals:**

- چنددانشگاهی و tenant routing، microservice، broker یا Redis اجباری، اپ موبایل مستقل، چت کامل و یادگیری ماشین.
- بازنویسی اجباری فرانت با فریم‌ورک جدید یا شماره‌گذاری فیزیکی تخت‌ها.
- تأیید علمی احتمال موفقیت هم‌اتاقی، تصمیم خودکار برای تخصیص نهایی مسکن یا انتشار عمومی بدون شواهد اپراتور.

## Decisions

### 1. معماری ماژولار در همان برنامه

بک‌اند به router، schema و serviceهای `auth`, `enrollment`, `privacy`, `matching`, `groups`, `rooms`, `notifications`, `operations` تفکیک می‌شود. سیاست eligibility و مرز تراکنش در service مشخص است؛ helperهای عمومی commit پنهان انجام نمی‌دهند. main فقط composition، middleware و lifespan را نگه می‌دارد.

فرانت به ES moduleهای `api/session`, `router`, `ui`, `features/student`, `features/admin` تبدیل می‌شود. یک shell و navigation مشترک، یک چرخهٔ بارگذاری برای هر انتقال route و لغو/نادیده‌گرفتن پاسخ قدیمی وجود دارد. CSS از tokenهای رنگ، فاصله، تایپوگرافی و اجزای مشترک استفاده می‌کند. استخراج تدریجی همراه تست قرارداد انجام می‌شود تا refactor و تغییر رفتار قابل‌تفکیک باشند.

دلیل: اندازهٔ پایلوت و stack فعلی نیازمند service مستقل یا مهاجرت فریم‌ورک نیست. جایگزین React/TypeScript بازنویسی گسترده‌ای ایجاد می‌کند و اکنون مزیت لازم برای رفع نقص‌ها ندارد؛ امکان ارزیابی بعدی حفظ می‌شود.

### 2. یک پایلوت، فهرست مجاز و دورهٔ تخصیص

پیکربندی شامل نام مؤسسه، یک `active_cycle`، اطلاعات پشتیبانی، سیاست نگهداری و poolهای مجاز خوابگاه است. `Enrollment` شامل شناسهٔ دانشجویی نرمال‌شده، ایمیل تأییدشدهٔ فهرست دانشگاه، pool تعیین‌شده توسط اپراتور، دوره و وضعیت است. اپراتور فهرست را با پیش‌نمایش خطا/تکرار import می‌کند؛ فایل اصلی import پس از پردازش نگهداری نمی‌شود.

Claim با توکن یک‌بارمصرف ارسال‌شده به ایمیل ثبت‌شده در فهرست انجام می‌شود و اتصال Enrollment به حساب unique است. آغاز ثبت‌نام فقط intent یا حساب pending غیرفعال می‌سازد؛ صاحب ایمیل پس از اعتبارسنجی دعوت، credential را تعیین/فعال می‌کند و رمز آغازگر ناشناس خودکار فعال نمی‌شود. ایمیل دلخواه همراه شمارهٔ دانشجویی برای claim کافی نیست. ایمیل یا pool اشتباه فقط با درخواست اصلاح و بررسی اپراتور تغییر می‌کند؛ معرف عمومی مانند نام قابلیت اصلاح با validation دارد. حساب خارج از فهرست به discovery یا عملیات گروه دسترسی ندارد؛ پاسخ‌های claim وجود حساب/شماره را افشا نمی‌کنند.

منبع eligibility، pool سازمانی است؛ جنسیت خوداظهاری به‌تنهایی مجوز تخصیص نیست. اتاق بدون pool یا دورهٔ معتبر برای تخصیص جدید بسته است. این مدل یک مرز سازمانی دارد و طراحی tenant عمومی نیست.

### 3. نشست قابل‌لغو و کنترل سوءاستفاده

JWT دسترسی دارای `sid`, `auth_version`, `sub`, `type`, `exp` است. هر درخواست احراز‌شده، کاربر فعال و session معتبر و هم‌نسخه را در DB بررسی می‌کند. lifetime دسترسی ۱۵ دقیقه و سقف مطلق session/refresh به‌طور پیش‌فرض ۷ روز است؛ refresh عمر مطلق را تمدید نمی‌کند. logout همان session را پیش از پاک‌کردن cookie لغو می‌کند. reset موفق در یک تراکنش hash رمز را عوض، token را مصرف، auth_version را زیاد و همهٔ sessionها را revoke می‌کند. نقش همچنان از DB خوانده می‌شود.

Login/refresh/reset ترتیب قفل `user -> session/auth-token` را رعایت می‌کنند و پس از قفل credential/version را دوباره بررسی می‌کنند. برای Argon2 خارج از قفل، نتیجه فقط وقتی معتبر است که hash/version زیر قفل تغییر نکرده باشد. replay refresh، session مربوطه را می‌بندد؛ فرانت refresh را single-flight و میان tabها هماهنگ می‌کند. درخواست‌های شروع‌شده پس از commit خروج/reset باید رد شوند؛ درخواست درحال‌اجرای پیش از آن قابل بازگرداندن نیست.

محدودسازی با bucket اتمیک PostgreSQL و `UPSERT RETURNING`، زمان DB، کلید HMACشدهٔ شناسه و action مجزا انجام می‌شود. رزرو سهمیه پیش از hashing/ایجاد کاربر/صف ایمیل و در تراکنشی مستقل commit می‌شود؛ شکست business transaction سهمیه را برنمی‌گرداند. همهٔ replicaها مرجع مشترک دارند؛ خرابی limiter در مسیر auth پاسخ قابل‌تلاش‌مجدد 503 می‌دهد.

پیش‌فرض‌های قابل‌پیکربندی برای NAT دانشگاه: login به ازای حساب ۲۰ و IP دویست تلاش در ۱۵ دقیقه؛ claim/register به ازای شناسه ۳ و IP شصت تلاش در ساعت؛ resend/forgot مجموعاً ۳ پیام به گیرنده در ساعت با فاصلهٔ حداقل ۶۰ثانیه، IP شصت در ساعت؛ مصرف token دعوت/verification/reset دویست تلاش IP در ۱۵ دقیقه. موفقیت A محدودیت B یا IP را پاک نمی‌کند. 429 دارای Retry-After است و حساب موجود را لو نمی‌دهد. تست onboarding پنجاه کاربر پشت NAT این defaults را ارزیابی می‌کند.

جایگزین JWT کاملاً stateless مشکل ابطال فوری را حل نمی‌کند؛ Redis برای این پایلوت وابستگی عملیاتی اضافی است. بار DB نشست/limiter اندازه‌گیری و محدودسازی قدیمی process-local حذف می‌شود.

### 4. مرز اطلاعات و چرخهٔ حساب

DTOهای owner، peer و operator صریح و allowlist هستند. peer هرگز پاسخ خام، شماره دانشجویی، ایمیل، ساعات دقیق یا وضعیت دخانیات را نمی‌گیرد؛ pending/accepted/same-group استثنا نیستند. owner پاسخ‌های خودش را می‌بیند؛ ادمین عملیاتی دسترسی پیش‌فرض به پاسخ خام ندارد. endpoint محاسبهٔ دلخواه میان دو کاربر حذف یا به جفت شامل خود کاربر با eligibility محدود می‌شود. cache خصوصی no-store باقی می‌ماند.

Discovery رضایت صریح برای نمایش نام/رشته و امتیاز کلی لازم دارد. دلیل‌های دسته‌ای تنها با opt-in نسخه‌دار هر دو نفر و allowlist موضوعات غیرحساس نمایش داده می‌شوند؛ هیچ توضیح دخانیات/اعتقادات یا علت شکست خط قرمز طرف مقابل ارائه نمی‌شود. opt-out فوراً روی درخواست‌های بعدی مؤثر است و approvalهای وابسته به اطلاعات قبلی را نامعتبر می‌کند. پرسش اعتقادات از نسخهٔ جدید حذف می‌شود.

Block، discovery و درخواست تازه را در دو جهت می‌بندد و دعوت‌های باز مربوط را با دلیل عمومی unavailable می‌بندد؛ عضویت/اتاق جاری را خودکار حذف نمی‌کند. گزارش مزاحمت وارد صف بررسی اپراتور می‌شود و خودکار مجازات ایجاد نمی‌کند. گزارش، نام گزارش‌دهنده و متن آن به طرف مقابل نشان داده نمی‌شود. محدودسازی و سقف متن برای این مسیرها لازم است.

درخواست حذف/انصراف فوراً discovery و sessionها را می‌بندد. حساب بدون تخصیص پس از انجام تسویهٔ منطقی گروه، دادهٔ مستقیم قابل‌شناسایی و پاسخ‌هایش پاک/ناشناس می‌شود. حساب تخصیص‌یافته تا خروج فردی توسط مدیر در وضعیت pending-closure می‌ماند؛ دیگران حفظ می‌شوند. فهرست مجاز از claim دوبارهٔ تصادفی حساب بسته‌شده جلوگیری می‌کند و بازگشایی نیازمند اپراتور است.

پیش‌فرض پیشنهادی پایلوت: audit تا ۹۰روز از ایجاد رویداد، تاریخچهٔ تخصیص pseudonymous تا ۹۰روز از بسته‌شدن تخصیص، محتوای گزارش تا ۳۰روز از ایجاد و backup چرخشی حداکثر ۳۰روز. گزارش باز نزدیک انقضا برای رسیدگی فوری escalate می‌شود. حذف دادهٔ اصلی پس از خروج عملیاتی فرد انجام می‌شود، دادهٔ backup با انقضای چرخه حذف می‌شود و restore باید ledger حذف‌ها را قبل از بازشدن دسترسی اعمال کند. این اعداد سیاست عملیاتی پیشنهادی‌اند؛ تنظیم و notice منتشرشده باید قبل از launch توسط مسئول دانشگاه تأیید شوند، نه اینکه الزام قانونی تلقی شوند. log/audit فاقد secret یا پاسخ خام است.

### 5. پرسشنامهٔ v2 و امتیاز قابل‌توضیح

هر نسخهٔ پرسشنامه schema ثابت دارد و هر submission یک revision دارد. پنج بعد اصلی: زمان معمول خواب، زمان بیداری، دفعات نظافت، دفعات مهمان و وضعیت سروصدا/مطالعه. ساعت‌ها local و در گام ۱۵دقیقه‌اند؛ بازهٔ پذیرفته‌شده می‌تواند از نیمه‌شب عبور کند. دادهٔ خود فرد و set/range قابل‌پذیرش از هم‌اتاقی جدا هستند. گزینه‌های دسته‌ای برچسب روشن دارند. هر بعد importance برابر ۱/۲/۳ با default دو و `hard_requirement=false` دارد؛ برای رفتار واقعی پاسخ پیش‌فرض اختراع نمی‌شود. دخانیات اختیاری با گزینهٔ عدم پاسخ است؛ اعتقادات جمع‌آوری نمی‌شود.

ابتدا active account/enrollment/cycle/pool، رضایت، پرسشنامهٔ جاری، block، عضویت/تخصیص و ظرفیت قابل‌پیوستن فیلتر می‌شوند. سپس خط قرمزهای دوطرفه بررسی می‌شوند؛ unknown، شرط سخت را برآورده نمی‌کند. امتیاز برابر `round_half_up(100 * satisfied_directed_weights / assessed_directed_weights)` (نیم‌واحد رو به بالا، نه bankers rounding) است. هر دو جهت A درباره B و B درباره A سنجیده می‌شود؛ بعد اختیاری نامعلوم از مخرج جهت مربوط کنار می‌رود. امتیاز «هم‌خوانی ترجیحات» است، نه احتمال موفقیت رابطه.

برای پیوستن به گروه، حضور عضو suspended یا pending-closure پذیرش جدید را تا حل عضویت متوقف می‌کند؛ چنین عضوی از بررسی حذف نمی‌شود. همهٔ جفت‌های candidate/member باید از شروط قطعی عبور کنند و امتیاز گروه کمینهٔ امتیاز این جفت‌هاست. ظرفیت ترجیحی set جدا از امتیاز است و از موجودی اتاق‌های مجاز دوره می‌آید. ایجاد گروه یک ظرفیت مشترک انتخاب‌شده می‌خواهد؛ عضو تازه باید همان ظرفیت را قبول کند. مرتب‌سازی score نزولی سپس شناسهٔ ثابت، pagination و limit حداکثر ۵۰ دارد؛ تعداد پیش‌فرض ۱۲. هیچ fallback فرد نامعتبر برای پرکردن لیست وجود ندارد. توضیح گروه رضایت candidate و تمام اعضایی را که در مقایسه مشارکت دارند لازم دارد. policy، purpose-aware است: discovery/admission شروط قابل‌پیوستن بودن دارند؛ مشاهدهٔ امن اعضای گروه جاری و تاریخچهٔ مجاز درخواست حتی پس از تخصیص ممکن می‌ماند، بدون اجازهٔ دعوت تازه یا افشای دادهٔ خصوصی.

Draft پرسشنامه owner-scoped در سرور ذخیره می‌شود؛ draft ناقص روی مچ فعلی اثر ندارد. submit اتمیک revision را عوض می‌کند و رضایت دعوت‌های متأثر نیازمند تأیید مجدد می‌شود. raw draft در localStorage ذخیره نمی‌شود. schema تغییرکرده به کاربر برای بازبینی نشان داده می‌شود.

### 6. درخواست و رضایت گروه

برای پایلوت group-to-group merge و پیوستن ضمنی همهٔ اعضا حذف می‌شود. دو نفر بدون گروه با دعوت و پذیرش ظرفیت مشترک گروه می‌سازند. افزودن فرد به گروه موجود نیازمند تأیید candidate و تمام اعضای فعلی است. Approval به membership revision، questionnaire revisions، ظرفیت، cycle و consent revisions بسته می‌شود؛ تغییر مؤثر، approval را نامعتبر و دعوت را `needs_reconfirmation` می‌کند.

وضعیت‌های درخواست `pending`, `needs_reconfirmation`, `accepted`, `rejected`, `cancelled`, `expired` هستند. دعوت هفت روز اعتبار دارد؛ انقضا در read/action و worker کنترل و notification تراکنشی ثبت می‌شود. reconfirmation مهلت اولیه را تمدید نمی‌کند. فقط اقدام منفی صریح `rejected` است؛ ازدست‌رفتن eligibility یا مهاجرت با `cancelled` و reason مشخص داخلی ثبت می‌شود. تأیید یک دعوت، دعوت‌های مستقل و هنوز معتبر را رد نمی‌کند. active invitation key در DB unique است و وضعیت‌های باز را پوشش می‌دهد.

هر transition terminal و تغییر membership در یک transaction است؛ فرمان تکراری برای وضعیت نهایی متفاوت 409 می‌دهد و side effect تازه ندارد. درخواست idempotency key با unique actor/action/key برای mutationهایی که امکان retry شبکه دارند نتیجهٔ همان فرمان را برمی‌گرداند. بازبینی eligibility در مرحلهٔ نهایی حتی بعد از approvals لازم است.

### 7. قفل‌ها، اتاق و خروج فرد

**تصمیم اجرایی پس از آزمون PostgreSQL:** برای این پایلوت کوچک، تمام mutationهای دامنه ابتدا قفل transaction-scoped مشترک `pg_advisory_xact_lock(7364202610)` می‌گیرند و identity map را expire می‌کنند. سپس دادهٔ جاری دوباره خوانده می‌شود؛ قفل‌های user/session/token در گردش امنیت پس از این مرز قرار می‌گیرند. این انتخاب، به‌جای الگوریتم پیچیدهٔ کشف و retry مجموعهٔ قفل چندگروهی، عملیات کوتاه دامنه را بین replicaها سری می‌کند؛ SMTP خارج از transaction است. اعتبار نشست و نقش در درخواست‌های تغییردهنده پس از گرفتن همین قفل دوباره بررسی می‌شود. این تصمیم مخصوص مقیاس محدود پایلوت است و آزمون بار شرط گسترش آن باقی می‌ماند. رقابت پذیرش/لغو، آخرین ظرفیت، تخصیص/پذیرش، تخصیص/خروج و تغییر پاسخ روی اتصال‌های مستقل آزموده می‌شوند.

رسید فرمان‌های دارای `Idempotency-Key` به actor/action/key و hash payload بسته می‌شود. دعوت، تخصیص/انتقال/لغو تخصیص، ساخت/ویرایش اتاق و تصمیم خروج نتیجهٔ همان فرمان را در transaction خود ثبت می‌کنند؛ تکرار فرمان قدیمی پس از انتقال تازه، اتاق را به عقب برنمی‌گرداند. پاسخ خطای validation فقط loc/type/msg دارد و مقدار ورودی رمز/توکن/پاسخ پرسشنامه را بازتاب نمی‌دهد.

مرز رتبه‌بندی فعلی حداکثر ۲۰۰۰ ورودی واجد شرایط و ۲۰۰۰ گروه در cohort است؛ عبور از آن خطای صریح ظرفیت پردازش می‌دهد و فهرست را خاموش truncate نمی‌کند. SQL مرتبط با هر candidate در حلقه اجرا نمی‌شود. پروتکل فرانت/API نسخهٔ `3` و پاسخ/درخواست `X-Matchsho-Protocol` دارد؛ نسخهٔ ناسازگار باید reload شود و mutation دوباره اجرا نمی‌شود.

مرجع transaction PostgreSQL با READ COMMITTED است. در اجرای پایلوت، قفل مشترک بالا پیش از دسترسی تغییردهنده به user/group/invitation/room/membership گرفته می‌شود و جایگزین نیاز به رقابت روی مجموعهٔ متغیر قفل‌های دامنه است. هیچ تصمیمی با relationship بارگذاری‌شده پیش از قفل گرفته نمی‌شود. در گردش امنیت، قفل user پیش از session/token است؛ login/reset/refresh که عضویت را تغییر نمی‌دهند فقط همین ترتیب امنیت را دارند. pool محدودسازی مستقل با ۲ اتصال ثابت و ۲ اتصال اضافه، از انتظار quota پشت connectionهای مشغول کسب‌وکار جلوگیری می‌کند. محاسبهٔ Argon2 با هزینهٔ اصلی و semaphore پیش‌فرض ۲ در هر پردازه، مصرف حافظه را محدود می‌کند.

GroupMember فعال برای هر کاربر unique و ظرفیت مثبت است. ظرفیت نهایی زیر قفل مشترک دوباره محاسبه می‌شود؛ دعوت/انصراف/تخصیص/تغییرپرسشنامه از همین serviceهای مشترک استفاده می‌کنند. شکست ذخیره‌ساز یا transaction پاسخ قابل‌تلاش‌مجدد دارد و هیچ پذیرش نیمه‌کاره‌ای commit نمی‌شود.

مدل تخصیص گروهی حفظ می‌شود. برای تخصیص جدید فقط یک گروه در هر اتاق مجاز است و ظرفیت فیزیکی اتاق باید با ظرفیت موردتوافق گروه برابر باشد؛ گروه ناقص فقط به تعداد اعضای واقعی occupancy دارد ولی جای خالی به گروه نامرتبط داده نمی‌شود. تخصیص‌های چندگروهی legacy حفظ و برای reconciliation علامت‌گذاری می‌شوند؛ unique constraint روی room_id تنها بعد از رفع این تعارض‌ها فعال می‌شود و تا آن زمان guard زیر قفل مشترک دامنه همین قاعده را برای عملیات جدید اجرا می‌کند. تنها ادمین assign/move/unassign کل گروه می‌کند؛ دانشجو برای خروج شخصی درخواست ثبت می‌کند. مدیر زیر قفل مشترک دامنه یک عضو را حذف، یک ظرفیت را آزاد و تخصیص سایرین را حفظ می‌کند؛ آخرین عضو باعث بسته‌شدن تخصیص خالی می‌شود. audit شامل قبل/بعد ظرفیت، actor، reason و request ID است و بدون پاسخ خام نگهداری می‌شود. در صورت انتقال، شمارش هر دو اتاق در همان transaction سری‌شده تغییر می‌کند.

مرجع occupancy تمام عضویت‌های جاری گروه‌های تخصیص‌یافته است، حتی اگر حساب عضو suspended یا pending-closure باشد؛ تغییر وضعیت حساب تخت را آزاد نمی‌کند.  ستون current_occupancy فقط cache کنترل‌شده در همان تراکنش است. reconciliation خطا را گزارش می‌کند و برای اصلاح قابل‌اثر روی تخصیص اجازهٔ تصمیم خودکار ندارد. گروه تخصیص‌یافته برای پیوستن self-service بسته است. اپراتور با reason می‌تواند عضو را خارج یا حساب را suspend کند، اما نمی‌تواند ظرفیت/eligibility را دور بزند.

### 8. outbox و اطلاع‌رسانی

`EmailOutbox` و notification در همان transaction رویداد کسب‌وکار ساخته می‌شوند. event/dedup key unique، purpose/template version، recipient، status، attempt، available_at، lease و خطای پاک‌سازی‌شده ذخیره می‌شوند. token احراز همچنان فقط hash است؛ raw link موردنیاز ارسال در payload رمز‌شده با کلید جداگانهٔ تحویل ایمیل قرار می‌گیرد. برای envelope از کتابخانهٔ استاندارد و بررسی‌شده مانند authenticated encryption در cryptography استفاده می‌شود؛ الگوریتم اختصاصی ممنوع است. key version برای rotation و جلوگیری از گم‌شدن پیام queued ثبت می‌شود.

worker مستقل، claim را با SKIP LOCKED و lease انجام می‌دهد، commit می‌کند و SMTP را بیرون transaction می‌فرستد. retry از ۳۰ثانیه با backoff تا سقف ۱۵دقیقه و حداکثر شش تلاش یا انقضای token ادامه می‌یابد. token باطل/منقضی/مصرف‌شده پیش از ارسال بررسی می‌شود. payload حساس پس از sent/terminal/expired پاک می‌شود. SMTP تضمین exactly-once ندارد؛ تحویل at-least-once با Message-ID ثابت و token یک‌بارمصرف مستند می‌شود.

UI موفقیت HTTP را «در صف ارسال» می‌نامد. پنل مدیر lag/failure/retry را بدون لینک بازیابی نشان می‌دهد. در development mail capture محلی و در production SMTP TLS و worker واقعی لازم است؛ چاپ لینک بازیابی در log جایگزین worker نیست. اعلان درون‌برنامه‌ای persistent برای درخواست، رأی، پذیرش، تخصیص و خروج فراهم می‌شود؛ preference ایمیل غیرامنیتی قابل‌کنترل است.

### 9. UI، دسترس‌پذیری و کارایی

لندینگ بدون splash اجباری محتوای واقعی دارد؛ menu موبایل در دسکتاپ مخفی و در موبایل واقعاً toggle می‌شود. تصویرهای تزئینی خارج از جریان layout هستند و عنوان/CTA در نمای اول قابل‌دیدند. فونت regular/bold درست map می‌شود؛ grid دسکتاپ از فضای موجود استفاده می‌کند و موبایل safe-area/navigation دارد.

route پروفایل شناسه دارد؛ refresh/back/forward همان شخص را از API بارگذاری می‌کند. navigation فقط یک‌بار data loader را اجرا می‌کند. owner draft، prefill و وضعیت dirty در فرم‌ها واضح است؛ خطای 401، 403، 404، 409، 429، شبکه و 5xx از empty جداست. پیام status از live region و انتقال focus پس از route پشتیبانی می‌کند. radio native از نوع visually-hidden و کارت‌ها link/button هستند؛ keyboard و reduced-motion آزموده می‌شوند.

نام/متن کاربر با textContent و attribute API ساخته می‌شود؛ interpolation HTML برای دادهٔ غیرقابل‌اعتماد حذف می‌شود. CSP دفاع مکمل است. build asset fingerprint تولید می‌کند؛ HTML revalidate و asset hashدار immutable cache می‌شود. بودجهٔ اولیهٔ لندینگ cold و فشرده حداکثر ۶۰۰KiB، لوگو ۴۰KiB و آواتار ۸۰KiB است؛ ابعاد، فرمت، responsive loading و lazy load خارج از نمای اول تعیین می‌شوند.

پنل ادمین جست‌وجو/صفحه‌بندی دانشجو، فهرست eligibility، گروه‌های آماده، تخصیص/خروج فرد، گزارش‌ها، تاریخچه و خروجی CSV دارد. خروجی فقط دادهٔ ضروری و دارای دفاع در برابر spreadsheet formula injection است. عملیات حساس پیش‌نمایش اثر، reason و نتیجهٔ قابل‌پیگیری دارند. ظاهر آماری تزئینی جای workflow را نمی‌گیرد.

### 10. استقرار و شواهد انتشار

مرورگر پیش‌فرض `/api` same-origin دارد؛ override development صریح است. public edge هدرهای forwarded ورودی را پاک/بازنویسی می‌کند؛ Nginx فقط ingress پیکربندی‌شده را برای real IP می‌پذیرد و Uvicorn فقط frontend proxy مجاز را trust می‌کند. wildcard trust حذف می‌شود. API و DB پورت عمومی ندارند. مسیر Compose و Kubernetes هر دو header-spoof test دارند؛ استقرار با proxy اضافی نیازمند تنظیم صریح است.

effective DATABASE_URL parse می‌شود؛ production به PostgreSQL با verify-full و CA معتبر نیاز دارد. استثنای اتصال بدون TLS فقط profile development محلی است. liveness فقط پردازه و readiness اتصال DB و schema/revision سازگار را بررسی می‌کند؛ outage SMTP جدا از readiness API پایش می‌شود.

Migration از startup replica جدا و با advisory lock یک‌بار اجرا می‌شود. Compose migration service و worker/mail-capture development دارد؛ Kubernetes از Job دارای release ID و image digest استفاده می‌کند. pipeline همان image ساخته‌شده را برای smoke مرورگر پشت Nginx واقعی تست می‌کند. Python 3.11 و PostgreSQL 16 مبنای تست production-like هستند؛ قفل/pinهای ابزارها با audit بررسی می‌شوند.

log ساخت‌یافته با request ID و metricهای latency/5xx/readiness/outbox/backup تولید می‌شود. مقصد هشدار واقعی قبل از launch آزموده می‌شود. backup روزانهٔ رمز‌شده بیرون host با retention حداکثر ۳۰روز؛ هدف آغازین RPO<=24h و RTO<=4h است و با restore اندازه‌گیری می‌شود. restore در DB جدا، worker خاموش و outbound email غیرفعال اجرا می‌شود؛ deletion ledger و invariantها پیش از بازشدن دسترسی اعمال می‌شوند. drill پیش از launch و سپس ماهانه انجام می‌شود.

آزمون بار staging: پنجاه session هم‌زمان با think-time واقعی به مدت ده دقیقه، p95 خواندن/مچ <=500ms، mutation <=1s، خطای 5xx کمتر از ۱٪ و صفر نقض invariant؛ hashing ورود و SMTP جداگانه اندازه‌گیری می‌شوند. این‌ها gate پیشنهادی پایلوت‌اند، نه ظرفیت اثبات‌شدهٔ host فعلی. CI امنیت، concurrency PostgreSQL، migration، browser، keyboard/RTL و scan dependency/secret/image را اجرا می‌کند.

## Risks / Trade-offs

- [نیاز به تکمیل دوبارهٔ پرسشنامه/claim] → پیام migration واضح، حفظ گروه/اتاق فعلی، کمک اپراتور و ممنوعیت تبدیل اهمیت v1 به رفتار جعلی v2.
- [تأخیر ورود فرد به گروه به‌دلیل رأی همه] → نمایش وضعیت رأی/انقضا و notification؛ ادغام پنهانی یا دورزدن رضایت برای ساده‌کردن UX مجاز نیست.
- [بار DB برای session/limiter/outbox] → index و cleanup، query bounded و سنجش واقعی؛ افزودن زیرساخت دیگر فقط با شواهد نیاز.
- [اختلاف نقش و قواعد خوابگاه] → pool و دوره در پیکربندی، عملیات نهایی مدیر و fail-closed برای دادهٔ ناقص؛ نام/قواعد واقعی پیش از launch تأیید می‌شوند.
- [تکرار ایمیل پس از crash در مرز SMTP] → Message-ID ثابت، token یک‌بارمصرف و قرارداد at-least-once؛ عدم ادعای exactly-once.
- [افشای استنباطی از توضیح مچ] → رضایت دوطرفه، allowlist دلیل غیرحساس و پیام عمومی برای عدم‌دسترسی؛ حذف دادهٔ خام/دخانیات/اعتقادات از توضیح.
- [rollback به API قدیمیِ ناامن] → نسخهٔ قدیمیِ فاقد privacy/session guard مقصد rollback نیست؛ release سازگارِ اصلاح‌شده یا forward-fix، maintenance و restore کنترل‌شده.
- [گزارش «آماده» بدون اجرای آزمون عملیاتی] → شواهد محیط واقعی جدا از completion کدنویسی؛ آیتم فاقد شاهد باز باقی می‌ماند.

## Migration Plan

1. از working tree موجود snapshot قابل‌بازگشت تهیه و schema/revision فعلی، داده و مسیرهای API ثبت شود؛ فایل‌های کاربر حفظ شوند. backup عملیاتی فقط در مرحلهٔ اجرا و با دسترسی واقعی انجام می‌شود.
2. preflight فقط خواندنی duplicate membership، capacity، occupancy، pool/cycle و roster conflicts را گزارش کند. تعارض معنادار نیازمند reconciliation اپراتور است؛ migration داده را حدس نمی‌زند یا عضو را خاموش حذف نمی‌کند.
3. Alembic revision جدید برای session/auth_version، enrollment/pool/cycle، پرسشنامه/consent revision، دعوت/approval، departure/report/block، outbox/notification و audit/history اضافه شود؛ baseline منتشرشده تغییر نکند. schema روی DB خالی و snapshot قبلی آزموده شود.
4. فاز expand با فیلدها/جدول‌های جدید اجرا شود. برای نسخهٔ ناسازگار، پنجرهٔ maintenance کوتاه و بستن mutationها پیش از cutover تعیین شود؛ backend/worker/frontend قدیمی و جدید بدون اثبات سازگاری هم‌زمان mutation نمی‌کنند.
5. حساب‌های قبلی نیازمند claim معتبر و v2 شوند؛ گروه/تخصیص حفظ شوند. اتاق فاقد pool برای تخصیص جدید بسته شود. دعوت legacy با reason `policy_upgrade` لغو و اعلان شود. JWT قدیمی فاقد sid/version رد شود و ورود مجدد لازم باشد. پاسخ v1 تا تکمیل مهاجرت فقط privately نگهداری و طبق retention پاک شود.
6. imageهای هماهنگ، schema revision و asset manifest منتشر و smoke انجام شوند. public launch فقط پس از TLS/SMTP واقعی، alert، restore، تست بار، notice و اپراتور تأییدشده انجام شود؛ شروع پیشنهادی ۲۰ تا ۵۰ دانشجوی داوطلب است.
7. rollback اپ با schema سازگارِ تست‌شده انجام شود؛ downgrade مخرب خودکار اجرا نشود. در صورت نیاز restore، mutationها بسته، صف ارسال قرنطینه، deletion ledger اعمال و داده‌های پس از backup با گزارش اپراتور reconcile شوند. شواهد زمان بازیابی و دادهٔ ازدست‌رفته ثبت شود.

## Open Questions

تصمیم معماریِ مانع شروع پیاده‌سازی باقی نمانده است. داده‌های محیطی زیر در launch checklist ثبت می‌شوند و تا تأمینشان شروع ترافیک واقعی مسدود است: نام/مالک پایلوت، active cycle و poolها، فهرست ایمیل مجاز و مسیر اصلاح آن، دامنه/CA/SMTP واقعی، مقصد backup/alert، مسئول پشتیبانی و تأیید retention/notice توسط دانشگاه. fixture و پیکربندی development برای تکمیل کد و آزمون مستقل فراهم می‌شوند؛ نبود این داده‌ها مجوز جعل شاهد عملیاتی نیست.
